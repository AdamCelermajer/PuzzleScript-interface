Qwen 3.8 27B on PuzzleScript

Adam Celermajer · 22 October 2026 · status after the 21 October experiment

Question. The 27B kept failing the games: harness, size, or pretraining? First: were the failures real?

Done. Fixed the infrastructure behind the earlier failures, then ran the same self-hosted 27B in 3 frameworks on 3 games.

Result. The premise changed. Driving the game itself with tools, the 27B solved Knightoban (6/6) and IceCrates (6/6) in its first attempt and reached 3/4 in Modality. It learns every visible mechanic and plays its own search plans at or near the shortest length; it never finds Modality's hidden floor-colour rule.

1. Is OpenCode better than Codex for the 27B?

Premise
On Modality the 27B went further under OpenCode (3 levels) than under Codex (level 1, then nothing).
Answer
No: the Codex run was broken, not worse. It ran through NanoGPT to save cost, and NanoGPT silently drops the tool format a recent Codex uses for MCP tools, so many of its moves never reached the game.
Found by
Codex's tool calls came back as plain text in the recorded requests; the same requests worked on OpenRouter; direct calls to NanoGPT: plain format 48/48, Codex's format 0/24.

2. Does quantization change cost, performance or capability?

Premise
OpenRouter and NanoGPT route each request to any host, at 16, 8 or 4 bits, unless one host is pinned: the same model name can be a different model per request.
Experiment
Modality, agent-driven, each group pinned to one host: 16-bit (DeepInfra), 8-bit (Chutes), 4-bit (ModelRun); 3 games each, stopped at 35 minutes. Performance = rules stated correctly (of 7), graded against the game's source.
Result
Precision matters. 16-bit learned most (17 of 21 rules) with the fewest wrong ones; 8-bit was cheapest but held the most wrong rules; 4-bit was worst: 4–11× the cost per game, and its reasoning collapsed into one repeated word in all 3 games. Host and precision can't be separated here, so the main experiment uses one self-hosted model.

3. What changed: from failing to solving

Main cause: context bloat. Most earlier failures came from what the 27B had to read and think over, not from what it can do. Every fix that unlocked play cut that context.

Frameworks, simplified

Baseline and Baseline+ are merged: both get a notes folder and a workspace; the only difference left is who drives the game. Turn-based: the controller sends one frame per turn, the player answers one action. Agent-driven: the player gets a goal and one tool that plays an action, and decides itself when to act, think, read notes or run a script.

The fixes

  • One current board as a small grid. The game tool returned every intermediate tick of a move: up to 7 boards, ~40k characters of JSON, the old board first. Now one plain grid; older boards on request.
  • Search out of the reasoning, into scripts. The agent-driven player writes its search in Python over its own rules and plays only the plan, so its context holds rules and plan, not the search. The turn-based player had the same tools but never wrote a script: it searched in its head before every move (3–5k tokens; once 63k tokens and 15 minutes).
  • Actions and tool calls conflicted. An action and a tool call in the same reply made the game miss actions and bloated the context. Now the action is its own tool call, act.py, which ends the turn.
  • No picture kept per turn. The turn-based player got the full image each turn and every past image stayed in the session (on 8 Oct it hit DeepInfra's 30-image limit). Now each turn gives only the path to frame.png; the player opens it with its read tool when needed.
  • Automatic compaction at ~200k tokens. OpenCode knows the 262k limit and reserves 64k for the answer, so it compacts at ~198k. Edge case left: thinking isn't counted, so one very long thinking step can still overflow (1 run killed, 6 recovered with lost context).
  • Working tools and one known model. OpenCode instead of Codex (plain tool format), and one self-hosted model instead of a host chosen per request.

Where context still grows, the 27B still degrades: it stops maintaining its notes and revising its rules after ~100 moves, and the Modality coaches hit the context limit with no edits.

4. Self-hosted setup

4 × RTX 5090 on vast.ai, vLLM, Qwen's official Qwen3.8-27B-FP8, 262k context, max thinking. ~84 tokens/s per call, 520–560 in total with 7–8 calls; 92% of input from the prefix cache. About $25 for the day.

What the numbers say

Agent-driven solves by inference plus its own search. Where its rules were right it played at or near the shortest (Knightoban levels 4–6: 41 / 31 / 28 vs 41 / 32 / 28); the extra moves are early learning and wrong beliefs (IceCrates water: 113 and 144 vs 29 and 8).

Turn-based is slower and can't run a plan. It thinks before every action. Still, on Modality levels 1–3 it used fewer moves (155 vs 404, one run each); on Knightoban it never finished level 1.

AVO never built a working solver, so it scored nothing. Its research sessions played well (IceCrates 5 levels in 101 moves), but an attempt counts only when its solver.py wins alone; Knightoban's sent ACTION5 500 times. Writing a general solver from scratch seems beyond the 27B; researching and playing are not.

How the agent-driven player plays

Unprompted, the same loop in every game (19 scripts in Knightoban, 12 in IceCrates, 7 in Modality):

  1. Probe single moves on the first level.
  2. Write the rules as a simulator, e.g. Knightoban's bfs.py: "Ring tile R is a portal. Moving in direction D into R requires center C = R + 2*D to be in-field."
  3. Search offline with BFS over that model; the scripts never call the game.
  4. Execute and check: play the plan, compare each real board with the predicted one, stop at the first mismatch (Knightoban level 4: "ALL 41 ACTIONS MATCHED").
  5. On a mismatch, fix the model and search again (IceCrates level 4: three versions, the last one searching under competing hypotheses).

70–83% of real moves were played in scripted bursts of 5+ (Knightoban 243/326, IceCrates 225/320, Modality 830/1000). In Modality the model is wrong (edge walls instead of the floor rule), so the loop becomes search on the real game: plan, bump, add a wall, re-plan; 596 moves on level 4 vs 158.

Across all runs

  • Visible mechanics are learned within tens of moves; a rule with no visible trace (Modality's floor colours) is never found: every refusal becomes a local wall.
  • A wrong belief survives as long as no plan depends on it (Knightoban's undo, from one misread move, later copied by the coach as verified).
  • What corrects a belief is a plan that fails: the agent-driven player's scripted plans forced retests; the turn-based player never failed sharply and stopped revising after ~100 moves.
  • Notes aren't kept even when asked: world_model.md barely changed in the agent-driven runs, and froze after ~100 moves in the turn-based ones.

The two coach prompts (dimension sections, verbatim)

Each mission is ~14k characters, mostly shared; one shared line matters: "VERIFIED FACTS ABOUT THIS WORKSPACE ARE THE MOST VALUABLE THING YOU CAN ENCODE … WRITE THE FACT ITSELF".

INV: how the agent works

You own procedure, tool use and completion -- not subject matter. Trace the workflow, fix its
earliest observed divergence, and match each failure to the cheapest effective component:
- TOOL ERROR: distinguish bad input from timeout, missing capability, permission, or unread output.
  Give one bounded fallback and stop condition; never prescribe blind repetition.
- MECHANICAL REPETITION: use `scripts/<name>.py` for repeated deterministic extraction,
  conversion or checking, with clear inputs, outputs and failure behavior.
- TRIGGERED WORKFLOW: use an on-demand skill for a narrow multi-step procedure, name its trigger
  in always-on text, and carry any helper it requires.
- IGNORED INVARIANT: only repeated evidence that clear prose is skipped can justify a defensive
  `plugin/<name>.ts` hook […] It must not block valid completion.
- ORDINARY SEQUENCING: prefer concise always-on guidance. Do not add code for a one-off mistake
  or automate professional judgment.
Define "enough evidence," reserve room for every artifact, and reopen or mechanically check the
environment model; a successful write call does not establish usability.
Improve observation, hypothesis tracking, notes, helper scripts that call `python game.py`,
planning, and recovery from dead ends.
Do not add professional rules, required domain sections or matter facts. A parallel candidate
owns them; stay focused on how the agent works.

DOM: what a practitioner knows

You own the practitioner model the agent lacks: the environment model, audience and decision,
controlling sources, required structure, consistency relationships, and expert omissions.
Turn it into checkable rules:
- ANALYTIC MOVE: name the operation -- compare, reconcile, calculate, classify, trace, draft or
  explain -- its inputs and required result.
- ARTIFACT CONTRACT: name required parts, their dependencies, and domain checks for consistency
  and practical use.
- DECISION RULE: state the trigger, supporting evidence, conflicts to resolve, and uncertainty
  that must remain explicit.
- ENCODING: […] A skill is the default home for domain knowledge that has a recognisable
  trigger […] Never store this matter's facts as durable memory: they are wrong anchors for
  the next task.
Use the observed transitions to learn this game's objects, controls, and goals.
Two hard rules:
- Never invent an authority, identifier, standard or citation. […]
- State knowledge the agent can APPLY and CHECK, not background reading.
Matter facts are in the supplied material. Say where to retrieve and reconcile them; never put
presumed facts into the harness.
Do not diagnose commands, retries, reading order, output paths, budgeting, scripts or hooks. A
parallel candidate owns procedure; stay on practitioner knowledge.

What the coaches built

On both solved games, both coaches turned base1's finished run into a ready-made solver: base1's rules marked as verified, a planning method, and a script that computes the plan from the current grid (solver.py, slide_sim.py, puzzle.py). No fixed move list: the path is recomputed from the board. INV added game knowledge too, although its prompt forbids it. Both also copied base1's wrong rules as verified (Knightoban's undo; Modality's edge walls).

Reading
Same-game coaching hands over the answer already found: optimal play in minutes. It doesn't make the player learn better, and when the found model is wrong it writes the error down as verified.

8. The premise, before and after

Before
"Qwen 3.8 27B fails at learning these games: harness, size or pretraining?"
After
With working tools, enough budget and the freedom to write its own search, it learns every visible mechanic and solves 2 of 3 games first try. It fails on a rule with no visible trace and keeps beliefs its play never contradicts. New question: under which conditions does it learn a game, and how can a hidden rule be revised?

Memorisation: all three games are public (Knightoban's levels 2–6 are Microban layouts), but prompts carry no title, tiles are anonymous, and the reasoning never names a game, author or "knight" ("Sokoban" only as an analogy). No sign of recall; exposure can't be excluded (H3).

10. Open issues

  • AVO never scored: every attempt must deliver a working solver. The levels-scored variant is built, not launched.
  • Compaction edge case: a very long thinking step can still overflow the context.
  • Modality coaching produced no harness, and what it started encoded the wrong model.
  • Turn-based Knightoban 0/6: an untested "off-board means blocked" belief made the target unreachable in its own model.
  • Single runs, three public games: the directions are clear, the sizes not yet.
